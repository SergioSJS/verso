# Load / bounds flood — VM 107, 2026-11-13 (ADR 0083 item 18)

Times in UTC-3. ADR 0083 item 18 was *measured* on 2026-10-15 but with the
note "**no flood was run**: nothing here was aimed at overwhelming the
server". This is that flood, against the same kind of host.

## Setup

- Target: the UniVerso test server on **Proxmox VM 107** (`verso-cloud`,
  1 core, 956 MB, Ubuntu 26.04), reachable on the LAN at
  `http://192.168.3.150:7340`. The owner authorized testing on the Proxmox
  VMs. Not a shared box (unlike ZimaOS), so a flood is fair here.
- The server ran `universo:rpg-cce63611b` (the deploy of 2026-11-02),
  container memory limit 544 MiB in this compose. Fake traffic only.
- Driver: `lab/hostile/load_probe.py` from the Mac over the LAN. The Mac is
  not a trusted proxy, so every connection counts against one address —
  the single-attacker-box case (per-address cap `PER_ADDRESS = 128`;
  total `CONNECTIONS = 512`, `listen.rs`).
- Container memory sampled once a second with `docker stats` throughout.

## Results

| Flood | What happened | Verdict |
|-------|---------------|---------|
| **Connections** — 300 sockets held open from one address at once | All 300 opened at TCP level; a fresh request from the same address while they were held was **reset** (the per-address budget of 128 is enforced by resetting the excess). After releasing them, `/api/state` → 200. | **held** |
| **Sign-ins** — 400 wrong sign-ins as fast as possible | **397 → HTTP 429**, 3 → 401. The rate limiter throttles the address within a few tries. No error, no crash. | **held** |
| **Requests** — 1000+ `GET /api/state` at concurrency 20 | Throttled to **HTTP 429 with `Retry-After: 1`** (a repeat gave 114 × 200, 886 × 429). The server sheds the burst with a status, it does not fall over. | **held** |
| **Memory** | Peaked at **44.6 MiB of the 544 MiB limit** (idle ~24 MiB) through all of the above — no growth toward the limit, no OOM. | **held** |
| **Survival** | `/api/state` → 200 after every flood. | **held** |

## Note on method

A first pass held the 300 sockets open *through* the sign-in and request
floods, so those floods hit the tester's own exhausted per-address budget and
every request reset — a tester error, not a server defect. Releasing the
sockets first gave the clean results above. Recorded so the run can be read
honestly.

## Not covered

- A distributed flood from many addresses (would need many source hosts or a
  trusted-proxy header spread, as the 2026-10-15 normal-use run simulated);
  this run is the single-address attacker.
- A sustained multi-minute soak; this was seconds-long bursts.
- The numbers in `docs/reference/server-install.md` §15 are unchanged: nothing
  here contradicted a published bound (item 18 says a contradicted number is
  changed in the same PR — none was).

## Verdict

Under a connection flood, a sign-in flood and a request burst from one
address, the 1-core / 1 GB server held every bound (per-address connection
reset, 429 rate-limiting with `Retry-After`, memory under 45 MiB) and stayed
up. Together with the HTTP and live-WebSocket runs
(`docs/review/2026-11-13-hostile-lab.md`), the automated hostile-lab side of
ADR 0083 items 18 and 19 is done; item 16's outside-person pentest still
gates the public announcement.
