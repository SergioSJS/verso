## Context

The demo content — the folder `demo-vault/`, which "Import the demo content"
writes into the open folder from a copy embedded in the app
(`app/ui/src/demoVault.ts`) — arrived in 0.3.0-beta.1 as a set of notes that
show what Verso does. It grew one note at a time, when someone remembered:
nothing said that a feature changes it, and the embedded copy was rebuilt by
hand. On 2026-09-30 it gained two boards, a tour of the platform and a lesson
in drawing on a board, generated by a script that lived outside the
repository.

## Decision

**Decided on 2026-10-01 by the maintainer**, in session:

1. **The demo vault is the product's tutorial.** Everything a user can do in
   Verso is taught in it, and what it teaches works as it says.
2. **Two boards lead it**: "Tour do Verso", the whole platform stop by stop,
   with the vault's notes live on its cards; and "Treino do Board", the board
   itself, Excalidraw included, lesson by lesson, each with something to try.
3. **Every change a user can see updates the tutorial**, in the same pull
   request, as it adds its line to the changelog
   ([0051](0051-development-flow-and-releases.md)): a note that teaches it, a
   card or a line on the tour, and, for the board, a lesson or a step of one.

How it is kept was the author's, for the maintainer to question; accepted by
the maintainer on 2026-10-01 (point 14):

4. **The tutorial's two boards are built from code.**
   `scripts/demo-vault/tour.mjs` and `scripts/demo-vault/treino.mjs` are their
   source; `node scripts/demo-vault.mjs build` writes them in the layout Verso
   writes (opening one writes nothing) and embeds the folder — the files git
   tracks — in the app. Neither is ever edited in the app and committed: the
   next build would undo it. The vault's third board, "Board de
   Demonstração", is kept by hand.
5. **What a board teaches is read as drawn text**, legible at the zoom a
   whole stop or lesson is seen at; a text card's Markdown is too small there.
   The notes stay notes, as cards.
6. **A key the tutorial teaches is checked** against Excalidraw's own key
   tests and the window's bindings before it is written, and the tutorial is
   followed in the app before the pull request, with the app's log open: a
   step that does not work is a bug of the app or of the tutorial, fixed in
   the same pull request. The walk is written down in
   [`demo-vault-walkthrough.md`](../reference/demo-vault-walkthrough.md):
   what to do, what must happen, how it is checked, and how far it runs by
   machine; a feature adds its own steps.
7. **`node scripts/demo-vault.mjs check`** — the boards are their modules'
   and the embed is the folder's, and the vault holds together: every link
   of a note or a board leads to a file of the vault and a `#heading` to one
   of its note's; the daily notes and the templates sit where the app looks
   by default; every numbered note is in the welcome note's map, on the tour,
   and links to the next one — runs in `scripts/check.sh` and in CI's
   pull-request job, as the generated bindings are checked
   ([0026](0026-core-ui-contract-inviolable-rules.md), rule 3).

`[OPEN]` **The demo vault in English.** The product is pt-BR and EN
([0035](0035-cross-cutting-requirements.md)); the demo vault has only ever
been in Portuguese, and nothing decided that. Until the maintainer decides,
it stays pt-BR.

**Decided on 2026-10-01 by the maintainer**, in session, on the walk run by
machine — what `check` and the unit tests do not cover, the window's own
behaviour:

8. **The walk runs by machine in the browser harness**, driven by
   Playwright's WebKit: headless, local, never takes the mouse or the
   keyboard; it grows with the app, and no one follows the walk by hand to
   know that it still works.

How it is kept was the author's, for the maintainer to question; accepted by
the maintainer on 2026-10-01 (point 14):

9. **The harness** (`app/ui/src/harness.ts` and `app/ui/src/harness/`) is
   the window over a core written in TypeScript: the demo vault in memory, or
   an empty folder (`?vault=empty`); every command of the contract answered
   with the contract's shapes and errors, through Tauri's own IPC mock, and
   later, as the real IPC answers; the `verso:` protocol served from the same
   memory; the app's log kept; the page under the app's own
   Content-Security-Policy. It is not the core: links, search and bases are
   answered roughly, enough for the window to behave; its writes are confined
   as the core's are, but a board's write lays the window's canvas out without
   the core's merge, it never holds a placeholder, and it sends no folder
   event after the window's own writes. What the core does is its Rust
   tests'. It is built apart from the app (`app/ui/e2e/build.mjs`, into
   `app/ui/e2e/.site/`) and never packaged.
10. **Every command of the contract has an answer in the harness.**
    `app/ui/e2e/harness.spec.mjs` reads `bindings.ts` and fails on a command
    the harness does not know: a new command arrives with its answer.
11. **A test fails on any trace of a fault**, besides what it asserts: an
    error on the console or of the page, a request that failed, an `ERROR` in
    the app's log, the window's work area not filling the window
    (`app/ui/e2e/fixtures.mjs`).
12. **The tests follow the walk**, one file of `app/ui/e2e/` per part of it;
    a step of [`demo-vault-walkthrough.md`](../reference/demo-vault-walkthrough.md)
    that runs by machine names its test, and a feature's pull request adds its
    steps with their tests.
13. **They run locally, not in CI**: `npm run e2e` in `app/ui`, and
    `scripts/check.sh` after the window's build, before every push. What the
    harness cannot reach stays by hand, and the walk says which: the real
    core, the app's `verso:` protocol, the Mac's menus and keys as the system
    delivers them (a menu's event is sent as the host sends it), files dropped
    from Finder, the updater, a file iCloud keeps in the cloud, and where
    WKWebView differs from Playwright's WebKit.
    *(`[REVISED 2026-11-04]` Still local, not in CI, but no longer natively on
    the Mac: `scripts/check-e2e.sh` runs both suites, the harness's and the
    server's, in Playwright's Linux Docker image, with 3 workers, and
    `scripts/check.sh` calls it when Docker runs (`--no-e2e` leaves it out).
    Playwright is never run directly on the Mac; see
    [0069](0069-windows-port.md), item 8. The suites and what the harness
    reaches are as above. `npm run e2e` in `app/ui` still exists, behind the
    macOS pre-flight.)*

**Decided on 2026-10-01 by the maintainer**, in session, on the critical
review [`docs/review/board.md`](../review/board.md), section 6, items 12
and 13: "Aceito todas (Recomendado)".

14. **Points 4 to 7 and 9 to 13 are accepted** as written above. The window's
    unit tests (`npm test` in `app/ui`) run in `scripts/check.sh` and in the
    pull request's job of CI ([0029](0029-guardrails-in-ci.md)); the
    end-to-end tests stay on the author's machine. *(`[REVISED 2026-11-04]`
    There they run through `scripts/check-e2e.sh`, in Docker; see point 13.)*
15. **The harness is never part of the app**: it is built outside `dist/`,
    which the app packages.

## Consequences

- `CLAUDE.md` §4 ("The PR") says it, beside the changelog line, in both
  languages.
- The checklist of what a feature's pull request touches grows by one item;
  a feature with nothing to show in the tutorial says so in the pull request.
- `scripts/check.sh` and `.github/workflows/ci.yml` run the check: a stale
  embed or a hand-edited board fails before review, not in a user's folder.
- The Python script that generated the boards on 2026-09-30 is replaced by
  the Node one in the repository (Node already builds the window).
- `docs/reference/demo-vault-walkthrough.md` is the walk: a feature's pull
  request adds its steps, each with the level it can run at by machine.
- `@playwright/test` (Apache-2.0) is a new development dependency of the
  window, never shipped; its WebKit is downloaded on the first run of
  `scripts/check.sh`.
- `npm run build` writes the app alone; the harness's page and script are
  built by Playwright's server into `app/ui/e2e/.site/` (point 15), and the
  unit tests' bundles go to `app/ui/test/.bundles/`, both outside what the
  app packages.
- The CI's minutes grow by the unit tests alone, seconds; the end-to-end
  tests run on the author's machine. *(`[REVISED 2026-11-04]` In Docker,
  through `scripts/check-e2e.sh`; point 13.)*

## Discarded alternatives

- **Boards kept by hand, edited in the app.** Considered by the author: an
  agent cannot edit a board in the app, and a hand-edited JSON of a hundred
  drawn elements is no place to add a lesson.
- **The real app on Linux**, in the container `scripts/check-linux.sh`
  already uses, driven by WebDriver (`tauri-driver` and WebKitWebDriver): the
  whole app, the core and the `verso:` protocol included, but not the Mac's
  menus and keys, and new tools in the image. Put to the maintainer on
  2026-10-01, who chose the harness.
- **The real app on the Mac**, driven by the system's input events and
  screen captures, as the walk was followed on 2026-10-01: everything, the
  Mac's menus and keys included, but it takes the mouse and the keyboard
  while it runs, finds things on the screen by position, and needs an agent
  to read what it sees. Put to the maintainer on 2026-10-01, who chose the
  harness.

### Amendment (2026-10-31): the site's wiki is made from the demo vaults

Source: the maintainer, in session, on 2026-10-31. A documentation wiki on the
site (versomd.com) for anyone with a question, built so that a person can also
paste its link into an AI assistant (ChatGPT, Gemini, Claude, Antigravity…) and
the assistant can read it to answer; no chat inside the site; links that open
an assistant with a prompt already filled in ("answer from this wiki, cite the
page"). And: "caso a gente altere alguma regra, talvez tenha que visitar os
arquivos de wiki também" (when a rule changes, the wiki's files may have to be
visited too). The author's plan, accepted the same day ("Boa, pode fazer"):

16. **The wiki has one source: the two demo vaults.** The site does not keep a
    second copy written by hand: a script of the site's repository imports the
    lessons of `demo-vault/` and `demo-vault-en/` as a snapshot it commits (the
    repository of the app is private, so the site's build cannot read it), and
    records the commit it came from. A page the wiki needs that the tutorial
    lacks (questions, problems, installing the server) is written as a note of
    the vaults, in both languages, like every lesson.
17. **Written for an assistant as much as for a person**: every page is static
    HTML readable without JavaScript and also served as Markdown (`.md`), with
    `/llms.txt` (an index of the pages, one line each on what it answers) and
    one `llms-full.txt` per language (the whole wiki in one file), so one link
    is enough for an assistant that reads only the page it is given. Each step
    a screenshot shows is also said in text.
18. **When a lesson, or a rule or behaviour a lesson describes, changes, the
    wiki is imported again** and the pages that describe it are read — in the
    pull request of the change, as the lesson is (point 3). The wiki's own
    pages of the site's repository (the index, the "ask an assistant" box) are
    visited when what they say changes.
